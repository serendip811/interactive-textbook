## 1. 문서의 역할

이 문서는 현재 프로젝트에서 **무엇을 만들고, 무엇을 먼저 만들 것인지**를 결정하는 Source of Truth다.

기존 문서는 다음과 같이 역할을 나눈다.

| 문서 | 역할 |
|---|---|
| `v0.2.md` | 현재 제품 정의, 핵심 결정, 개발 순서와 완료 기준 |
| `v0.1-platform.md` | 장기 플랫폼·기술 아키텍처 참고 문서 |
| `v0.1-notebook.md` | 실험, 실패, 아이디어와 의사결정 근거를 기록하는 작업 노트 |
| `v0.1-file.md` | v0.2 이전의 제품 기획 기준 문서 |

세부 기술 명세는 이 문서에서 모두 확정하지 않는다. 실제 구현과 검증을 통해 별도 문서로 구체화한다.

## 2. 한 문장 정의

> **화성학에서 검증한 ‘개념을 직접 보고·듣고·조작하며 이해하는 학습 경험’을 재사용 가능한 교재 엔진으로 만들고, 서로 다른 두 번째 교재에서 이를 검증한 뒤 플랫폼으로 확장한다.**

학습자에게 보이는 제품의 가치는 다음과 같다.

> **글로만 이해하기 어려운 개념을 직접 보고, 듣고, 움직이고, 비교하며 익히는 인터랙티브 교재**

내부에서 만드는 기술 제품은 다음과 같다.

> **구조화된 학습 데이터와 재사용 가능한 표현·활동·판정 도구로 여러 인터랙티브 교재를 실행하는 교재 엔진**

AI는 제품의 목적이 아니다. 좋은 교재를 더 빠르고 일관되게 만들고 검수하기 위한 핵심 제작 수단이다.

---

## 3. 현재 단계에 대한 판단

현재 프로젝트는 아이디어 검증 단계가 아니다.

화성학 교재 RC1을 통해 다음 경험이 이미 구현 가능하다는 것을 확인했다.

- PART 0~16, 총 76개 단원
- 개념 설명, 악보, 건반, 오디오, 연습, 요약과 문제의 연결
- VexFlow 기반 악보
- Web Audio 기반 재생
- 전체 진행과 한 단계씩 듣기
- 재생 단계와 건반 하이라이트 동기화
- 자유 건반
- 파트별 체크포인트와 즉시 채점
- 음정 문제와 반음 수 시각화
- 모바일 목차와 반응형 화면

화성학 RC1은 완성된 플랫폼 위에 올라간 교재는 아니다. 그러나 **인터랙티브 교재가 어떤 경험이어야 하는지를 보여주는 강력한 PoC이자 기준 구현체**다.

현재의 핵심 과제는 화성학 페이지에 기능을 계속 추가하는 것이 아니다.

> 화성학 안에서 이미 작동하는 학습 경험을 의미 데이터, 표현, 조작, 판정, 학습 상태와 플레이어로 분해하고 재사용 가능한 구조로 만드는 것이 다음 단계다.

## 4. 현재 구조의 한계

- 약 5,800줄의 단일 HTML에 콘텐츠와 실행 코드가 결합되어 있다.
- 콘텐츠, 악보, 건반, 오디오, 문제와 채점 로직의 경계가 불명확하다.
- 새 교재를 만들려면 기존 HTML을 복제하고 직접 수정해야 한다.
- 비슷한 설명과 관찰형 연습이 여러 단원에 반복된다.
- 기능 수정이 다른 단원의 동작에 영향을 줄 가능성이 있다.
- 진도, 응답, 오답과 마지막 위치가 지속적으로 저장되지 않는다.
- 콘텐츠와 엔진의 버전 및 검수 이력이 분리되어 있지 않다.
- 외부 CDN 의존성, 키보드 조작과 재생 상태 등 기술 품질을 보완해야 한다.
- 화성학에 맞춰 만들어진 구조가 다른 과목에서도 유효한지는 검증되지 않았다.

현재 HTML은 폐기하지 않는다. 기능과 콘텐츠 오류는 계속 고치되 구조적인 기능 추가는 최소화한다. RC1은 다음 용도로 보존한다.

- 작동하는 학습 제품
- 새 엔진의 화면·재생·채점 비교 기준
- 데이터 추출 원본
- 회귀 테스트 기준

## 5. 핵심 개발 방향

### 5.1 플랫폼을 먼저 만들지 않는다

프로젝트를 다음 순서로 진행한다.

```text
화성학 RC1
→ 대표 단원 분해와 재구축
→ 교재 엔진 v0.1
→ 작은 두 번째 교재
→ 공통 구조 재검증
→ 교재 엔진 v0.2
→ 화성학 전체 이전
→ 제품·제작·배포 플랫폼
```

처음부터 회원, 교재 목록, 검색, CMS, 공개 편집기, 결제와 마켓을 만들지 않는다. 이러한 서비스 기능은 핵심 학습 엔진이 검증된 후 추가한다.

### 5.2 두 번째로 좋은 교재를 만들 수 있어야 한다

첫 번째 화성학 교재가 수작업으로 만들어졌다는 사실만으로는 플랫폼 가능성이 증명되지 않는다.

엔진의 첫 성공 조건은 다음과 같다.

> 기존 구현을 복제하지 않고 화성학의 서로 다른 단원을 만들 수 있으며, 같은 엔진으로 화성학과 구조가 다른 작은 두 번째 교재도 만들 수 있어야 한다.

### 5.3 두 번 이상 검증된 기능만 공통화한다

처음부터 모든 과목을 위한 완벽한 블록 체계를 설계하지 않는다.

다음 조건을 충족할 때 공통 기능으로 승격한다.

- 서로 다른 단원 또는 교재에서 두 번 이상 사용되었다.
- 실행 코드를 복제하지 않고 데이터 변경만으로 재사용할 수 있다.
- 특정 과목의 의미를 제거해도 공통 역할이 명확하다.
- 학습 목표에 실질적으로 기여한다.

한 과목에서만 필요한 기능은 과목별 도구로 유지한다.

## 6. 프로젝트의 핵심 자산

이 프로젝트의 핵심은 블록의 개수가 아니다.

> **하나의 학습 의미 데이터를 여러 표현, 조작과 판정이 공유하는 구조가 핵심 자산이다.**

### 6.1 화성학 예시

```text
Chord 데이터
├── 악보 표현
├── 건반 표현
├── 음 이름 표현
├── 오디오 재생
├── 화음 구성 활동
├── 화음 판별
└── 정답과 피드백 근거
```

예를 들어 C단3화음은 단순한 `[C4, Eb4, G4]` 문자열 배열만으로 충분하지 않다. 같은 소리라도 `C♯`과 `D♭`은 화성학적으로 다른 의미를 가질 수 있기 때문이다.

음 데이터는 최소한 표기와 소리를 함께 보존해야 한다.

```ts
type Pitch = {
  step: "C" | "D" | "E" | "F" | "G" | "A" | "B";
  alter: -2 | -1 | 0 | 1 | 2;
  octave: number;
  midi: number;
};
```

여기에 길이, 시작 시점, 성부, 조성, 기능과 화음 관계를 필요한 수준에서 추가한다.

### 6.2 함수와 그래프 예시

```text
Function 데이터
├── 수식 표현
├── 값의 표
├── 좌표 그래프
├── 계수 슬라이더
├── 입력과 출력 계산
└── 문제 판정과 피드백
```

화성학과 함수는 표현 도구는 다르지만 다음 핵심 구조를 공유한다.

```text
개념 데이터
→ 여러 표현
→ 학습자 조작
→ 결과 변화
→ 판정과 피드백
```

이 구조가 두 과목에서 성립하는지를 확인하는 것이 플랫폼화의 첫 검증이다.

## 7. 엔진의 구조

엔진은 다음 여섯 영역으로 구분한다.

```text
Interactive Book Engine
├── Content Schema       교재·파트·단원·블록 구성
├── Domain Models        음정·화음·함수 등 학습 의미 데이터
├── Views                악보·건반·오디오·그래프 등 표현
├── Activities           선택·입력·이동·재생·비교 등 조작
├── Validators           정답·규칙·조건 판정과 피드백
├── Player               탐색·렌더링·접근성·반응형 UI
└── Learning State       진도·응답·오답·마지막 위치
```

### 7.1 콘텐츠 스키마

교재의 계층을 정의한다.

```text
Book
└── Part
    └── Lesson
        └── Block
```

각 단원은 학습 목표, 선수 단원, 예상 학습시간, 블록 목록과 완료 조건을 가질 수 있다.

### 7.2 학습 구성 블록

단원의 흐름을 구성하는 공통 요소다.

- 본문과 강조 설명
- 이미지와 미디어
- 비교
- 단계별 설명
- 선택형 문제
- 짧은 입력 문제
- 힌트와 피드백
- 요약과 복습

초기에는 필요한 최소 블록만 구현한다. 문서에서 예상했다는 이유만으로 모든 블록을 미리 개발하지 않는다.

### 7.3 과목 의미 모델

특정 과목의 개념을 구조화한 데이터다.

- 음악: `Pitch`, `Interval`, `Chord`, `Progression`, `VoiceLeading`
- 수학: `Point`, `Function`, `Line`, `Parameter`, `Intersection`

과목 의미 모델은 UI 컴포넌트가 아니다. 여러 표현과 활동이 함께 사용하는 원본 데이터다.

### 7.4 View

의미 데이터를 학습자가 이해할 수 있는 형태로 표현한다.

- 음악: 악보, 건반, 음 이름, 오디오, 단계 표시
- 수학: 수식, 표, 좌표 그래프, 변화 애니메이션

같은 의미 데이터를 바라보는 View들은 상태가 서로 일치해야 한다.

### 7.5 Activity와 Validator

Activity는 학습자가 수행하는 행동이고 Validator는 그 결과를 판단한다.

예:

- 건반에서 목표 음정 만들기
- 음을 선택해 화음 구성하기
- 진행을 듣고 종지 판별하기
- 음표를 움직여 병행 5도 수정하기
- 기울기 값을 바꾸고 그래프 변화 예측하기

판정은 단순한 정답 여부를 넘어 다음 정보를 제공할 수 있어야 한다.

- 무엇이 맞거나 틀렸는가
- 어떤 규칙을 다시 확인해야 하는가
- 다음 시도에서 무엇을 바꿔야 하는가
- 복수 해석이나 부분 정답이 가능한가

### 7.6 학습 상태

학습 상태는 플랫폼 이후의 부가기능이 아니라 엔진의 기본 책임이다.

초기 엔진은 최소한 다음을 저장한다.

- 마지막으로 본 교재와 단원
- 단원별 시작·완료 상태
- 활동 완료 여부
- 문제별 응답, 정오와 시도 횟수
- 오답과 재시도 상태
- 콘텐츠 버전

초기에는 계정 없이 브라우저 로컬 저장을 사용한다. 계정, 서버 동기화와 기기 간 이어보기는 이후 제품 계층에서 추가한다.

## 8. 콘텐츠 포맷 원칙

초기 기준은 다음과 같다.

- 규격 정의: JSON Schema
- 개발 단계 타입: TypeScript
- 긴 본문 작성: Markdown
- 사람이 직접 작성하는 보조 형식: YAML 허용
- 플레이어 입력: 검증과 변환이 끝난 JSON

콘텐츠와 실행 엔진은 별도로 버전 관리한다.

모든 주요 객체는 안정적인 ID를 가진다.

```yaml
book:
  id: harmony-foundations
  version: 0.2.0

lesson:
  id: intervals-build-major-third
  objectives:
    - id: build-major-third
      text: 기준음에서 장3도를 만들 수 있다.

  blocks:
    - id: explanation-1
      type: content.markdown
      objective_refs: [build-major-third]
      content: 장3도는 음이름으로 3도이고 반음으로 4칸이다.

    - id: activity-1
      type: music.interval-builder
      objective_refs: [build-major-third]
      data_ref: interval-example-c4-m3
      validation:
        target_interval: M3
      feedback:
        incorrect: 음이름의 거리와 반음 수를 함께 확인하세요.
```

정답과 해설을 의미 데이터에서 자동으로 유도할 수 있는 경우에는 중복 입력을 피한다. 다만 교육적 설명은 기계적 판정과 다를 수 있으므로 해설 전체를 무조건 자동 생성하지 않는다.

## 9. 학습 경험 원칙

### 9.1 읽기에서 조작으로

학습자는 완성된 결과를 보기만 하지 않는다. 학습 목표에 도움이 되는 경우 값을 바꾸거나 대상을 움직이고 결과를 직접 확인한다.

### 9.2 하나의 개념, 여러 표현

글, 기호, 그림, 소리와 움직임은 서로 분리된 장식이 아니라 동일한 개념을 다른 방식으로 보여줘야 한다.

### 9.3 즉시 피드백

정답 여부뿐 아니라 판단 근거와 다음 행동을 알려준다.

### 9.4 목표에 맞는 상호작용

모든 단원에 동일한 조작이나 문제 형식을 반복하지 않는다. 상호작용이 이해를 돕지 않는다면 억지로 넣지 않는다.

### 9.5 유연한 학습 흐름

다음 흐름을 기본 원칙으로 사용하되 고정된 화면 순서로 강제하지 않는다.

```text
설명 → 탐색 → 조작 → 예상과 결과 비교 → 적용 → 피드백 → 회상
```

### 9.6 정확성이 화려함보다 우선

멋진 애니메이션보다 콘텐츠의 정확성, 정답과 해설의 타당성, 여러 표현의 일치가 먼저다.

## 10. 초기 사용자와 제품 형태

초기 학습자는 화성학을 기초부터 독학하려는 입문자로 설정한다.

- 음악을 배우지만 화성학 개념이 추상적으로 느껴지는 사람
- 악보 설명만으로 음정과 화음을 이해하기 어려운 사람
- 영상보다 자신의 속도로 탐색하고 반복하려는 사람

초기 사용자에게는 범용 플랫폼보다 **완성도 높은 화성학 인터랙티브 교재**로 제공한다.

내부에서는 동일한 제품을 교재 엔진의 첫 기준 구현체로 사용한다.

## 11. AI의 역할

### 11.1 초기부터 사용하는 내부 AI

- 기존 HTML에서 콘텐츠와 예제 데이터 추출
- 기존 콘텐츠를 스키마 형식으로 변환
- 반복 설명과 유사 문제 탐지
- 학습 목표, 설명, 문제와 해설의 불일치 후보 탐지
- 악보·건반·오디오 데이터의 불일치 후보 탐지
- 함수 교재와 변형 문제 초안 생성
- 스키마 검사와 테스트 사례 생성 보조

### 11.2 엔진 검증 후 만드는 사용자용 AI

- 학습 대상과 목표를 입력받아 커리큘럼 초안 생성
- 학습 목표에 맞는 블록·View·Activity 추천
- 의미 데이터와 문제 초안 생성
- 제작자 편집과 미리보기
- 자동 검증 리포트
- 사람 검수와 승인 후 배포

### 11.3 AI 사용 원칙

- AI는 임의 HTML이나 JavaScript를 생성해 바로 공개하지 않는다.
- 생성 결과는 플랫폼 규격 안의 검수 가능한 초안으로 저장한다.
- AI가 만든 정답과 해설은 별도 검증 대상이다.
- 공식 교재는 사람의 검수를 통과해야 한다.
- 생성·수정·검수 이력을 내부적으로 기록한다.
- 서비스의 전면 메시지는 AI가 아니라 인터랙티브한 이해 경험이다.

## 12. 화성학 RC1 운영 원칙

RC1은 동결하되 방치하지 않는다.

허용하는 변경:

- 악보·건반·오디오 불일치 수정

- 모바일 화면 깨짐과 접근성 문제 수정
- 심각한 성능 문제 수정

최소화하는 변경:

- 새로운 플랫폼 기능 추가
- 대규모 UI 재설계
- 새 상태 관리 구조를 기존 단일 HTML에 누적
- 다른 과목을 기존 HTML 구조에 추가

새 기능은 가능하면 새 엔진에서 구현한다.

## 14. 두 번째 교재 검증

화성학 전체를 이전하기 전에 **함수와 그래프 미니 교재**를 만든다.

### 14.1 선정 이유

- 화성학과 전혀 다른 과목이다.
- 개념 데이터와 여러 표현의 연결이 분명하다.
- 값을 조작했을 때 결과 변화가 즉시 나타난다.
- 공통 본문·문제·피드백·진도 구조를 재사용할 수 있다.
- 새로운 과목별 도구를 함수 그래프 중심으로 제한할 수 있다.
- 짧은 범위에서도 하나의 완결된 학습 경험을 만들 수 있다.

수영처럼 3D 인체, 관절, 물과 저항을 동시에 다뤄야 하는 분야는 초기 범용성 검증 대상으로 선택하지 않는다.

### 14.2 첫 검증 단원

1. 좌표와 점
2. 함수의 입력과 출력
3. 일차함수의 기울기
4. 절편의 변화
5. 두 직선의 교점

### 14.3 검증할 사항

- 화성학에서 만든 공통 블록을 그대로 재사용할 수 있는가
- 플레이어와 학습 상태가 과목에 종속되어 있지 않은가
- `math.function-graph` 같은 새 과목 도구를 독립적으로 추가할 수 있는가
- 함수 하나의 데이터가 수식·표·그래프·조작·판정을 함께 만들 수 있는가
- 과목별 코드를 수정하지 않고 공통 엔진을 개선할 수 있는가

두 과목에서 반복되어 확인된 요소만 공통 엔진 기능으로 확정한다.

## 16. 검수와 품질 기준

### 16.1 콘텐츠 품질

- 학습 목표, 설명, 예제, 활동과 평가가 서로 일치한다.
- 정답과 해설이 검증되어 있다.
- 같은 개념의 용어와 표기가 일관된다.
- 선수 지식과 난이도가 학습자 수준에 맞는다.
- 복수 해석이 가능한 문제를 단일 정답으로 처리하지 않는다.

### 16.2 의미 데이터 품질

- 여러 View가 같은 원본 데이터를 사용한다.
- 악보, 건반, 음 이름과 오디오가 일치한다.
- 표기상 다른 음을 MIDI 번호 하나로 합치지 않는다.
- 데이터 수정이 관련 표현과 판정에 일관되게 반영된다.
- 중복 입력으로 인해 서로 다른 정답이 생기지 않는다.

### 16.3 상호작용 품질

- 무엇을 조작해야 하는지 별도 설명 없이 이해할 수 있다.
- 조작 결과가 즉시 나타난다.
- 잘못된 입력에서 복구할 수 있다.
- 재생 중 현재 단계가 명확하다.
- 피드백이 정답 여부와 이유를 함께 제공한다.
- 활동이 장식이 아니라 학습 목표에 기여한다.

### 16.4 기술 품질

- 콘텐츠 수정과 엔진 코드 수정이 분리된다.
- View, Activity와 Validator를 독립적으로 테스트할 수 있다.
- 데이터 및 엔진 버전을 관리할 수 있다.
- 모바일과 키보드 사용이 가능하다.
- 외부 라이브러리 의존성과 오프라인 정책이 명확하다.
- 오류가 다른 단원이나 교재로 전파되지 않는다.

### 16.5 자동 검사

- 스키마 유효성
- 필수 필드 누락과 중복 ID
- 끊어진 데이터 참조
- 정답과 선택지 불일치
- 음정·화음·표기 규칙
- 여러 음악 표현의 데이터 일치
- 깨진 에셋과 허용되지 않은 외부 리소스
- 접근성 레이블 누락
- 모바일 화면 넘침
- 지원하지 않는 블록과 엔진 버전

## 17. 단계별 성공 조건

### Engine v0.1 성공 조건

- 대표 단원이 기존 HTML 복사 없이 데이터로 구성된다.
- 악보·건반·오디오가 동일한 음악 의미 데이터를 공유한다.
- 전체 듣기와 단계별 듣기에서 화면 상태가 동기화된다.
- 최소 세 종류의 조작형 활동이 판정과 피드백까지 연결된다.
- 새로고침 후에도 진도와 응답이 유지된다.
- 콘텐츠 변경에 엔진 코드 수정이 필요하지 않다.

### Cross-subject Validation 성공 조건

- 함수 단원이 화성학과 동일한 플레이어에서 실행된다.
- 공통 블록과 학습 상태를 수정 없이 재사용한다.
- 함수 그래프 도구가 음악 코드와 분리되어 있다.
- 화성학에 특화된 가정을 제거해도 기존 단원이 정상 작동한다.
- 두 과목에서 반복된 구조와 과목별 구조의 경계가 설명 가능하다.

### 화성학 v2 성공 조건

- 76개 단원의 내용과 정답이 누락 없이 이전된다.
- 반복적이고 관찰 중심인 활동이 개선된다.
- 악보·건반·오디오 불일치가 자동 또는 수동 검수된다.
- 모바일과 데스크톱에서 핵심 기능이 동일하게 작동한다.
- 콘텐츠 수정과 엔진 배포를 독립적으로 수행할 수 있다.

### 플랫폼 전환 조건

다음 조건을 충족한 후 제작기와 공개 플랫폼 개발을 본격화한다.

- 두 개 이상의 서로 다른 교재가 동일 엔진에서 동작한다.
- 새 단원 제작 시 실행 코드를 직접 수정하는 비율이 충분히 낮다.
- 공통 블록과 과목별 도구의 경계가 안정적이다.
- 콘텐츠 검수와 버전 관리 방식이 실제 제작 과정에서 검증됐다.
- 학습자가 인터랙션을 실제로 사용하고 학습에 도움이 된다는 근거가 있다.

초기에는 가입자 수보다 학습 경험과 제작 구조의 유효성을 측정한다.

- 조작형 활동 참여와 완료율
- 첫 시도와 재시도 후 정답률
- 오답 복습 완료율
- 단원별 중도 이탈 지점
- 조작 전후 개념 이해 변화

### 제작 지표

- 새 단원 제작 소요 시간
- 코드 수정 없이 만들 수 있는 단원 비율
- 공통 View·Activity·Validator 재사용률
- 콘텐츠 변경에 필요한 코드 수정 횟수
- 자동 검사가 배포 전에 발견한 오류 수
- 기존 단원에서 발생한 회귀 오류 수

### 품질 지표

- 정답과 해설 오류 건수
- 여러 표현 사이의 불일치 건수
- 접근성 및 모바일 오류 수
- 배포 후 수정이 필요한 콘텐츠 비율
- 검수 완료되지 않은 콘텐츠의 공개 건수

---

## 19. 현재 확정하는 결정

1. 제품의 중심 가치는 AI가 아니라 직접 조작하며 이해하는 학습 경험이다.
2. 초기 사용자에게는 범용 플랫폼이 아니라 화성학 인터랙티브 교재로 제공한다.
3. 화성학 RC1은 PoC이자 기준 구현체로 보존한다.
4. 기존 단일 HTML에 플랫폼 기능을 계속 누적하지 않는다.
5. 플랫폼보다 교재 엔진을 먼저 만든다.
6. 핵심 자산은 블록 목록이 아니라 의미 데이터를 여러 표현·활동·판정이 공유하는 구조다.
7. 학습 구성 블록과 과목 의미 모델을 구분한다.
8. 학습 상태는 플랫폼 부가기능이 아니라 엔진의 기본 책임이다.
9. Engine v0.1은 화성학 대표 단원 4~5개로 검증한다.
10. 화성학 전체 이전 전에 함수와 그래프 미니 교재로 범용성을 검증한다.
11. 실제로 두 번 이상 반복된 기능만 공통 기능으로 승격한다.
12. 초기 진행 기록은 계정 없이 로컬 저장으로 시작한다.
13. AI는 내부 제작과 검수에 초기부터 사용하되, 사용자용 AI 제작기는 나중에 만든다.
14. 공개 제작기, 마켓과 외부 제작자 기능은 엔진과 콘텐츠 규격이 안정된 후 개발한다.

## 20. 하지 않을 것

- 단순 HTML 파일 호스팅 서비스로 만들지 않는다.
- 처음부터 모든 과목을 지원하는 범용 엔진을 설계하지 않는다.
- 사용 여부가 검증되지 않은 블록을 미리 대량 구현하지 않는다.
- 화성학 전체 이전을 두 번째 과목 검증보다 먼저 완료하지 않는다.
- 모든 단원에 동일한 학습 순서와 문제 형식을 강제하지 않는다.
- 학습 목표와 관계없는 애니메이션과 조작을 추가하지 않는다.
- AI가 만든 콘텐츠를 검수 없이 공식 교재로 공개하지 않는다.
- 임의 HTML과 JavaScript를 공식 콘텐츠 규격으로 사용하지 않는다.
- 첫 버전부터 회원, 마켓, 결제와 고급 분석을 만들지 않는다.

## 24. 최종 비전

이 프로젝트는 전자책을 예쁘게 보여주는 서비스가 아니다. 교재마다 별도의 HTML을 만들어 모아두는 저장소도 아니며, 처음부터 모든 과목과 제작자를 지원하는 거대한 교육 마켓도 아니다.

> **학습자는 하나의 개념을 여러 표현으로 보고 직접 조작하며 이해하고, 제작자는 검증된 학습 도구와 AI를 이용해 정확한 인터랙티브 교재를 만들며, 엔진은 그 과정의 실행·상태·판정·검증을 책임진다.**

화성학은 이 비전의 첫 번째 결과물이자 출발점이다. 함수와 그래프는 엔진이 화성학 전용 구조를 넘어설 수 있는지 확인하는 첫 번째 시험이다.

두 교재에서 검증된 공통 구조가 쌓였을 때 비로소 교재 엔진을 제작·검수·배포 플랫폼으로 확장한다.

현재 우리가 만드는 것은 거대한 플랫폼의 빈 껍데기가 아니다.

> **좋은 첫 번째 교재에서 출발해, 좋은 두 번째 교재를 만들 수 있는 엔진을 만드는 것이다.**
