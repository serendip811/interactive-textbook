# 인터랙티브 교재 플랫폼 기획서

> 버전: v0.1  
> 문서 성격: 제품 정의 및 초기 실행 계획  
> 기준 구현체: 인터랙티브 화성학 교재

---

## 1. 한 문장 정의

> **AI와 재사용 가능한 인터랙티브 학습 블록을 활용해 교재를 만들고, 검증하고, 배포하고, 학습할 수 있는 플랫폼을 만든다.**

학습자는 글과 영상을 수동적으로 보는 데서 그치지 않고, 개념을 직접 조작하고 듣고 비교하며 즉시 피드백을 받는다.

제작자는 기능을 처음부터 코딩하지 않고도 공통 학습 블록과 과목별 도구를 조합하고, AI의 도움을 받아 인터랙티브 교재를 제작한다.

AI는 플랫폼의 목적이 아니라 **좋은 교재를 더 빠르고 체계적으로 만드는 핵심 제작 수단**이다.

---

## 2. 프로젝트가 시작된 이유

기존 디지털 교재는 종이책을 화면으로 옮기거나 영상 강의를 제공하는 데 머무는 경우가 많다. 학습자는 설명을 읽고 예제를 보지만, 개념을 직접 움직이고 결과를 비교하는 경험은 제한적이다.

화성학 교재를 실제 HTML로 제작하면서 다른 가능성을 확인했다.

- 악보를 보면서 같은 음을 건반에서 확인할 수 있다.
- 악보와 건반의 내용을 실제 소리로 들을 수 있다.
- 전체 진행과 단계별 진행을 비교할 수 있다.
- 문제를 풀고 즉시 채점과 해설을 받을 수 있다.
- 하나의 데이터를 악보·건반·오디오라는 여러 표현으로 연결할 수 있다.

이 경험은 단순한 전자책보다 발전된 학습 방식이 실제로 구현 가능하다는 것을 보여준다. 동시에 하나의 거대한 HTML 파일만으로는 여러 교재와 과목으로 확장하기 어렵다는 한계도 드러냈다.

따라서 다음 단계의 목표는 화성학 페이지에 기능을 계속 덧붙이는 것이 아니다.

> **화성학 교재에서 검증된 학습 경험을 데이터, 블록, 과목별 도구, 공통 플레이어로 분리해 재사용 가능한 교재 엔진을 만드는 것**이 다음 단계다.

## 3. 현재 위치

### 3.1 화성학 교재

현재 화성학 교재는 다음을 포함한 강력한 개념증명(PoC)이다.

- PART 0~16, 총 76개 단원
- 개념·악보·건반·연습·요약·문제의 공통 단원 구조
- VexFlow 기반 악보 시각화
- Web Audio 기반 재생
- 건반 하이라이트와 단계별 진행
- 전체 진행 및 한 단계씩 듣기
- 자유 건반
- 파트별 체크포인트와 객관식 문제
- 즉시 채점과 해설
- 모바일 목차와 반응형 UI
- 음정 퀴즈와 반음 수 시각화

이 교재는 “인터랙티브 교재가 어떤 느낌인지”를 보여주는 대표 작품이자 플랫폼 설계의 기준 구현체로 충분한 가치가 있다.

### 3.2 현재 수준에 대한 판단

| 영역 | 현재 판단 |
|---|---|
| 화성학 콘텐츠 | 전체 교육과정의 외형을 갖춘 완성도 높은 프로토타입 |
| 인터랙티브 학습 | 악보·건반·소리 연결은 강력하지만 관찰형 활동의 비중이 큼 |
| 학습 제품 | 진도·오답·검색·북마크·접근성·검증 체계 보완 필요 |
| 공통 플랫폼 | 비전과 핵심 경험은 검증됐지만 공통 구조는 아직 분리되지 않음 |
| 확장 가능성 | 충분히 크지만 현재 단일 HTML 구조로 확장하면 한계가 빠르게 발생 |

### 3.3 현재 구조의 한계

- 콘텐츠, 디자인, 악보, 오디오, 건반, 문제, 채점 로직이 한 파일에 결합돼 있다.
- 새 교재를 만들려면 기존 HTML을 복제하고 직접 수정해야 한다.
- 유사한 학습 흐름과 연습 문구가 여러 단원에 반복된다.
- 일부 기능은 기존 스크립트 위에 새로운 이벤트를 덧붙이는 방식으로 누적돼 있다.
- 콘텐츠 수정이 다른 기능의 동작에 영향을 줄 가능성이 있다.
- 진도, 퀴즈 결과, 오답, 북마크, 메모가 지속적으로 저장되지 않는다.
- 외부 CDN 의존성 때문에 완전한 오프라인 사용을 보장하기 어렵다.
- 임의 HTML을 그대로 확장하면 보안, 접근성, 모바일 품질, 디자인 통일을 관리하기 어렵다.

현재 HTML은 폐기하지 않는다. 작동하는 원본과 비교 기준으로 보존하되, 새 플랫폼의 데이터 규격이나 코드 기반으로 직접 사용하지 않는다.

## 4. 제품이 해결하려는 문제

### 학습자의 문제

- 추상적인 개념을 글만 읽고 이해하기 어렵다.
- 설명, 그림, 소리, 실습이 서로 분리돼 있다.
- 틀린 이유를 바로 알기 어렵다.
- 학습 진도와 오답이 쌓이지 않아 복습이 단절된다.
- 모든 단원에 같은 학습 방식이 반복되어 개념별 차이가 충분히 드러나지 않는다.

### 제작자의 문제

- 인터랙티브 교재 한 권을 만들려면 콘텐츠와 프론트엔드 기능을 함께 개발해야 한다.
- 악보, 그래프, 시뮬레이션 같은 도구를 교재마다 새로 구현한다.
- AI로 초안을 만들 수 있어도 결과의 형식과 품질이 일정하지 않다.
- 내용, 예제, 정답, 해설의 일관성을 체계적으로 검증하기 어렵다.
- 수정과 배포, 버전 관리가 하나의 작업 흐름으로 연결되지 않는다.

### 플랫폼이 제공할 해법

- 교재 내용을 구조화된 데이터로 저장한다.
- 공통 학습 블록을 조합해 단원을 구성한다.
- 악보·건반·그래프·시뮬레이터 등 과목별 도구를 플러그인처럼 연결한다.
- 하나의 학습 데이터를 여러 표현과 상호작용에 재사용한다.
- AI가 규격 안에서 초안 작성, 변환, 점검을 돕는다.
- 제작자 검수와 자동 검증을 통과한 버전만 배포한다.
- 학습자의 진도, 응답, 오답, 북마크를 지속적으로 관리한다.

## 5. 핵심 학습 철학

### 5.1 읽기에서 조작으로

학습자는 완성된 예제를 보기만 하는 사람이 아니라 개념을 직접 바꾸고 결과를 확인하는 참여자다.

### 5.2 하나의 개념, 여러 표현

같은 개념을 텍스트, 그림, 소리, 기호, 수식, 움직임 등으로 연결한다. 표현은 서로 독립된 장식이 아니라 동일한 학습 데이터를 공유해야 한다.

### 5.3 즉시 피드백

문제의 정답 여부만 알리는 데서 끝나지 않고, 왜 맞거나 틀렸는지와 다음에 무엇을 확인해야 하는지를 알려준다.

### 5.4 공통 원칙과 유연한 단원 구성

모든 단원에 동일한 순서를 강제하지 않는다. 제작자는 학습 목표에 따라 블록을 조합하되 다음 공통 원칙을 따른다.

> 설명 → 탐색 → 연습 → 피드백 → 정리

이 흐름은 기본 템플릿이지 고정된 화면 구조가 아니다.

### 5.5 필요한 곳에만 시각화와 조작 적용

- 추상적인 개념은 가능한 한 눈에 보이는 표현으로 바꾼다.
- 조작이 이해에 도움이 되는 지점에서는 학습자가 직접 실험하게 한다.
- 시각화나 상호작용이 학습에 도움이 되지 않는다면 억지로 추가하지 않는다.

### 5.6 정확성이 화려함보다 우선

멋진 인터랙션보다 내용, 정답, 예제, 표현 간 일치가 먼저다. AI가 만든 결과도 자동 공개하지 않고 검증 가능한 상태로 관리한다.

## 6. 제품의 네 영역

| 영역 | 주요 사용자 | 핵심 역할 |
|---|---|---|
| 교재 라이브러리 | 학습자 | 교재 탐색, 검색, 저장, 이어보기 |
| 학습 플레이어 | 학습자 | 콘텐츠 실행, 조작, 채점, 진도 및 복습 |
| 교재 제작기 | 제작자 | 블록 편집, AI 초안 생성, 미리보기 |
| 검증·배포 시스템 | 제작자·운영자 | 오류 검사, 검수, 버전 관리, 공개 |

초기에는 학습 플레이어와 공통 엔진에 집중한다. 완전한 공개형 제작기와 마켓은 학습 엔진과 콘텐츠 규격이 검증된 뒤 확장한다.

## 7. 플랫폼 구조

```text
서비스
├── 교재 라이브러리
├── 학습 플레이어
├── 교재 제작기
└── 검증·배포 시스템

공통 교재 엔진
├── 교재·파트·단원 탐색
├── 블록 렌더링
├── 문제 채점과 피드백
├── 진도·오답·북마크·메모
└── 반응형 UI와 접근성

공통 학습 블록
├── 본문
├── 이미지·SVG
├── 단계별 시각화
├── 비교
├── 선택형 문제
├── 직접 입력 문제
├── 요약
└── 복습 세트

과목별 플러그인
├── 음악: 악보·건반·오디오·화성 분석
├── 수학: 수식·좌표·함수 그래프
├── 물리: 힘·운동·파동 시뮬레이터
├── 화학: 분자 구조·반응 시각화
└── 프로그래밍: 코드 실행·상태 추적

교재 콘텐츠
├── 화성학
└── 이후 추가 교재
```

### 계층별 책임

| 계층 | 책임 |
|---|---|
| 교재 데이터 | 제목, 목표, 설명, 예제, 문제, 정답, 해설 |
| 학습 블록 | 데이터를 화면과 상호작용으로 표현 |
| 과목별 플러그인 | 특정 과목의 전문 표현과 조작 제공 |
| 학습 플레이어 | 탐색, 상태 관리, 저장, 반응형 UI 제공 |
| 검증 시스템 | 데이터 형식, 정답, 연결 관계, 접근성 검사 |
| 제작 도구 | 블록 추가, 편집, 미리보기, AI 보조 제공 |

핵심 원칙은 **콘텐츠 데이터와 실행 코드를 분리하는 것**이다.

## 8. 콘텐츠 모델

교재는 다음 계층으로 구성한다.

```text
교재 Textbook
└── 파트 Part
    └── 단원 Lesson
        └── 학습 블록 Block
            └── 데이터·상태·피드백
```

### 예시 데이터

```yaml
textbook:
  id: harmony-basics
  title: 인터랙티브 화성학
  version: 0.1.0

lesson:
  id: interval-2-1
  title: 음정이란
  objectives:
    - 두 음의 도수를 계산할 수 있다

  blocks:
    - id: concept-1
      type: content.markdown
      content: 두 음 사이의 거리를 음정이라고 한다.

    - id: music-example-1
      type: music.note-relation
      data:
        notes: [C4, E4]
      views: [score, keyboard]
      playback:
        modes: [together, ascending]

    - id: practice-1
      type: music.interval-builder
      prompt: C4를 기준으로 장3도를 만들어 보세요.
      validation:
        targetInterval: M3
      feedback:
        correct: C에서 E까지는 장3도입니다.
        incorrect: 음이름의 개수와 반음 수를 함께 확인하세요.

    - id: quiz-1
      type: assessment.multiple-choice
      question: C에서 E까지는 몇 도인가?
      choices: [2도, 3도, 4도]
      answer: 3도
      explanation: C-D-E를 양 끝 음까지 포함하여 센다.
```

이 데이터 하나로 악보, 건반, 재생, 채점, 해설을 서로 일치시켜야 한다.

### 블록 공통 규격

모든 블록은 가능한 한 다음 공통 필드를 갖는다.

- `id`: 단원 안에서 고유한 식별자
- `type`: 블록 종류와 네임스페이스
- `data` 또는 `content`: 표시할 내용
- `state`: 학습 중 변경 가능한 상태
- `interaction`: 조작 방식
- `validation`: 정답 또는 조건 검사 규칙
- `feedback`: 성공·오류·힌트 메시지
- `accessibility`: 대체 텍스트, 레이블, 키보드 동작
- `analytics`: 기록할 학습 이벤트

## 9. 블록 설계 원칙

### 9.1 공통 블록

초기 버전에서는 다음 8~10개에 집중한다.

1. 본문 및 강조 설명
2. 이미지·SVG
3. 단계별 시각화
4. 비교
5. 선택형 문제
6. 직접 입력 문제
7. 순서 배열 또는 연결
8. 요약
9. 복습 세트
10. 과목별 인터랙티브 도구 컨테이너

### 9.2 과목별 블록

과목별 기능은 공통 블록과 구분된 네임스페이스를 사용한다.

```text
content.markdown
content.compare
assessment.multiple-choice
assessment.text-input
music.notation
music.keyboard
music.playback
music.interval-builder
math.function-graph
physics.force-simulator
```

### 9.3 화성학의 조작형 활동

화성학의 각 개념에는 동일한 연습 형식이 아니라 목표에 맞는 상호작용을 적용한다.

| 개념 | 권장 상호작용 |
|---|---|
| 반음·온음 | 건반 위에서 거리를 직접 세기 |
| 음정 | 두 번째 음을 움직여 목표 음정 만들기 |
| 화음 | 구성음을 직접 선택해 화음 만들기 |
| 자리바꿈 | 베이스음을 이동해 자리바꿈 완성하기 |
| 종지 | 여러 진행을 듣고 유형 판별하기 |
| 전조 | 공통화음을 찾아 두 조를 연결하기 |
| 성부 진행 | 음표를 움직여 병행 5도·8도 수정하기 |
| 화성 분석 | 악보의 화음에 로마숫자 붙이기 |

## 10. AI의 역할

AI는 임의의 HTML을 만들어 바로 공개하는 도구가 아니다. 플랫폼이 허용한 콘텐츠 모델과 블록 규격 안에서 제작과 검증을 보조한다.

### 1단계: 내부 제작 보조

- 학습 목표를 바탕으로 단원 초안 작성
- 개념에 적합한 블록 조합 추천
- 예제와 문제 후보 생성
- 기존 HTML 내용을 구조화된 데이터로 변환
- 설명·예제·정답·해설 간 불일치 탐지
- 난이도 및 표현 개선 제안

### 2단계: 제한된 제작자 지원

- 학습 대상과 목표 입력
- 단원 구조와 활동 추천
- 규격에 맞는 초안 생성
- 제작자 수정 및 검수
- 자동 검사 후 배포 요청

### 3단계: 일반 사용자 제작

- 검증된 블록만 사용해 교재 제작
- 공개 전 자동 검사와 운영 정책 적용
- 제작자 이력과 교재 버전 표시
- 신고, 수정 요청, 비공개 전환 절차 제공

### AI 사용 원칙

- AI 생성 여부보다 결과의 정확성과 학습 효과를 평가한다.
- AI가 만든 정답과 해설은 별도 검증 대상이다.
- AI가 임의 스크립트나 실행 코드를 삽입하지 못하게 한다.
- 생성 결과는 즉시 공개하지 않고 검수 가능한 초안으로 저장한다.
- 중요한 변경은 누가, 언제, 무엇을 수정했는지 기록한다.

## 13. 임의 HTML 가져오기에 대한 원칙

플랫폼의 중심 규격은 임의 HTML이 아니라 구조화된 교재 데이터다.

임의 HTML을 핵심 입력 방식으로 삼지 않는 이유는 다음과 같다.

- 스크립트 충돌과 보안 위험
- 디자인과 상호작용 품질의 불일치
- 진도와 정답을 플랫폼이 이해하기 어려움
- 모바일·접근성 품질을 보장하기 어려움
- 콘텐츠와 기능을 다시 재사용하기 어려움

현재 화성학 HTML은 자동·수동 변환을 위한 원본으로 사용한다. 향후 외부 HTML을 지원하더라도 별도 격리 환경에서 제한적으로 실행하며, 공식 교재 포맷과는 구분한다.

## 14. 화성학 교재 이전 계획

76개 단원을 한 번에 옮기지 않는다. 서로 다른 학습 패턴을 대표하는 10~15개 단원을 먼저 선택해 엔진을 검증한다.

### 이전 순서

1. 기존 HTML과 기능을 기준 구현체로 동결·보존한다.
2. 단원, 예제, 문제 데이터를 추출한다.
3. 공통 콘텐츠 스키마와 음악 데이터 스키마를 정의한다.
4. 본문·예제·퀴즈·요약 공통 블록을 구현한다.
5. 악보·건반·오디오 음악 블록을 분리한다.
6. 대표 단원 10~15개를 새 엔진으로 옮긴다.
7. 기존 HTML과 화면·음정·재생·채점 결과를 비교한다.
8. 개념별 조작형 활동 4~6종을 추가한다.
9. 스키마와 블록 API를 안정화한다.
10. 나머지 화성학 단원을 단계적으로 이전한다.

### 대표 단원 선정 기준

- 단순 설명 중심 단원
- 악보·건반·오디오가 동시에 필요한 단원
- 단계별 재생이 필요한 단원
- 음정과 반음 수 계산 단원
- 화음 구성 단원
- 듣기 판별 단원
- 직접 조작형 활동이 필요한 단원
- 체크포인트와 종합 복습 단원

### 이전 완료 기준

- 기존 내용과 정답이 누락되지 않는다.
- 악보, 건반, 오디오가 동일한 데이터를 사용한다.
- 전체 듣기와 단계별 듣기에서 화면 상태가 동기화된다.
- 모바일과 데스크톱에서 동일한 학습 기능을 제공한다.
- 문제 응답과 오답이 새로고침 후에도 유지된다.
- 핵심 기능에 키보드 접근이 가능하다.
- 콘텐츠 수정이 엔진 코드 수정 없이 가능하다.

## 15. MVP 범위

### MVP 1: 학습 엔진 증명

목표는 여러 과목을 지원하는 것이 아니라, 화성학 일부를 구조화된 데이터로 실행할 수 있음을 증명하는 것이다.

포함:

- 교재·파트·단원·블록 데이터 구조
- 공통 학습 플레이어
- 본문·예제·선택형 문제·요약 블록
- 음악 악보·건반·오디오 블록
- 전체 및 단계별 재생 동기화
- 진도와 오답 저장
- 화성학 대표 10~15개 단원 이전
- 모바일 대응과 기본 접근성

제외:

- 누구나 사용하는 완전한 노코드 제작기
- 공개 교재 마켓
- 결제와 정산
- 임의 HTML 업로드
- 여러 과목의 동시 지원
- AI 자동 공개
- 교사·학생 조직 관리

### MVP 2: 콘텐츠 확장성 증명

- 화성학 전체 이전
- 조작형 음악 활동 4~6종
- 검색, 북마크, 메모, 이어보기
- 복습 세트와 오답 관리 강화
- 두 번째 교재 제작
- 두 교재에서 반복되는 요소만 공통 기능으로 승격

### MVP 3: 제작 플랫폼 증명

- 내부 블록 편집기
- AI 단원 초안과 문제 생성
- 자동 검증 리포트
- 미리보기와 버전 관리
- 제한된 제작자의 검수·배포

## 16. 두 번째 교재 선정 원칙

두 번째 교재는 화성학과 지나치게 비슷해서도, 완전히 다른 기술을 대량으로 요구해서도 안 된다.

선정 기준:

- 화성학에서 만든 공통 블록을 상당 부분 재사용할 수 있는가
- 새로운 과목별 도구가 1~2개 정도만 필요한가
- 직접 조작의 학습 효과가 분명한가
- 내용 검증이 가능한가
- 짧은 범위로도 완결된 교재를 만들 수 있는가

초기 후보는 음악이론 또는 시각적 수학 주제가 적합하다. 두 번째 교재를 통해 실제로 반복된 요소만 공통 플랫폼 기능으로 확정한다.

## 19. 핵심 의사결정

이 문서에서 확정하는 방향은 다음과 같다.

1. 플랫폼의 목적은 AI 콘텐츠 생성 자체가 아니라 좋은 인터랙티브 학습 경험이다.
2. AI는 제작과 검증을 돕는 핵심 수단으로 사용한다.
3. 현재 화성학 HTML은 강력한 PoC이자 기준 구현체로 보존한다.
4. 현재 HTML을 계속 확장하지 않고 데이터와 공통 블록을 추출해 새 엔진을 만든다.
5. 플랫폼의 공식 규격은 임의 HTML이 아니라 구조화된 교재 데이터다.
6. 모든 단원에 같은 6단 구조를 강제하지 않는다.
7. 공통 학습 원칙 안에서 개념별로 가장 적합한 상호작용을 선택한다.
8. 초기 제품은 학습 플레이어와 교재 엔진에 집중한다.
9. 화성학 전체를 한 번에 이전하지 않고 대표 단원으로 구조를 먼저 검증한다.
10. 완전한 제작기와 공개 마켓은 엔진과 콘텐츠 규격이 안정된 뒤 만든다.

## 20. 아직 결정해야 할 사항

- 초기 핵심 학습자는 독학 성인, 전공 입문자, 교사 수업 보조 중 누구인가
- 화성학 대표 이전 단원 10~15개는 무엇인가
- 콘텐츠 포맷은 YAML, JSON, MDX 중 무엇을 기준으로 할 것인가
- 음악 데이터의 단일 원본은 음 이름, MIDI 번호, 악보 이벤트 중 무엇인가
- 학습 기록을 로컬 우선으로 시작할지 계정 기반으로 시작할지
- 교재 내용 검수 책임과 승인 권한을 누가 가질지
- 두 번째 교재를 음악이론과 수학 중 무엇으로 선택할지
- 오프라인 지원을 MVP에 포함할지 후속 단계로 둘지
- AI 생성 콘텐츠와 사람이 작성한 콘텐츠의 표시 정책을 어떻게 할지

## 22. 최종 비전

이 플랫폼은 전자책을 예쁘게 보여주는 서비스가 아니다. 교재마다 독립된 HTML을 모아두는 호스팅 서비스도 아니다.

> **학습자는 개념을 직접 조작하며 이해하고, 제작자는 AI와 재사용 가능한 학습 도구를 이용해 인터랙티브 교재를 만들며, 플랫폼은 그 과정의 실행·기록·검증·배포를 책임진다.**

화성학 교재는 이 비전의 첫 결과물이다. 이제부터의 과제는 화성학 교재를 더 거대한 단일 파일로 만드는 것이 아니라, 그 안에서 검증된 학습 경험을 누구나 다시 사용할 수 있는 구조로 바꾸는 것이다.

현재 프로젝트는 아이디어 단계가 아니다.

> **화성학 웹페이지를 계속 보완하는 단계에서, 화성학을 기준 구현체로 삼아 인터랙티브 교재 엔진을 만드는 단계로 넘어간다.**
